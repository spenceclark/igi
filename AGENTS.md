# Rules

While you may have access to "Cairn" code via the environment, do not make any changes to Cairn via this session. Only edit code under IGI folder.

- `docs/spec.md` is the specification. Revise it in place; don't append contradictory notes.
- `docs/progress.md` is the progress log. Append note as things are completed. Record issues found and resolved.
- This repository is public. `docs/private/` is gitignored and holds notes on Cairn internals: never copy its content into tracked files, and never link to the private Cairn repository from public docs.
- `server/` is the Node/TypeScript backend. Node 24+ runs `.ts` files directly, so use erasable TypeScript syntax only (no `enum`, no parameter properties). In `server/`: `npm run smoke:monty` checks the Monty sandbox (spec §9); `npm run probe:meta` calls the Meta Model API (`-- --vessel` routes it through the local Vessel proxy, as `investigate` can); `npm run probe:cairn` makes one read-only status request to Cairn; `npm run cairn -- <open|submit|status|pack|submit-pack|withdraw|new-version> <review>` drives a review against real Cairn, where `open --start`, `submit` and `submit-pack` write, so run those only when the user asks.
- Type every value precisely in `server/`: declare the shapes of data crossing a boundary (model responses, Cairn responses, database rows, tool arguments), and use `unknown` with narrowing where a shape is genuinely open. Use `any` only where no type can be written, with a comment giving the reason. `strict` in `server/tsconfig.json` passes an explicit `any`, so this rule is the check.
- Comment code in `server/` for a reader coming to it fresh: a `/** */` header on every function saying what it does and why (citing the spec section where one applies), a `//` note on each exported type, and a comment above any block whose purpose the code doesn't make obvious (a query, a rounding rule, a stopping condition). Comments use neutral examples such as 12.34%, never a scenario's figures or names.
- Secrets live only in the environment or `server/.env` (gitignored): the Meta key `MODEL_API_KEY`, the Cairn agent key `CAIRN_AGENT_KEY` (with `CAIRN_BASE_URL`, `CAIRN_SUBJECT_REFERENCE` and `CAIRN_PROCEDURE_NAME`), and later the database connection and the Spaces keys. Never read, print or commit them. IGI's database and bucket are its own; never connect to Cairn's database or storage.
- In `server/`: `npm test` runs the unit tests (they print PDFs with Puppeteer's pinned Chrome); `npm run typecheck` runs the type check; `npm run investigate -- ../fixtures/scenarios/dev-01 [--review <id>] [--vessel]` runs a Spark investigation (costs about $0.20; `--review` starts a fresh review on the same sources; `--vessel` sends the model requests through Vessel at `VESSEL_URL`, default `127.0.0.1:4550`, tagged `spark`, in a session named after the run, for inspection with the Vessel MCP tools), saving the run and its trace in the local IGI database. `npm run db:up` starts that database: a Docker container `igi-postgres` on port 5434, separate from Cairn's; tests use their own `igi_test_*` databases (`test/helpers.ts`) and skip when it isn't running. `npm start` serves the API and the built UI on port 8080; it needs `OPERATOR_PASSWORD` set, and `SESSION_SECRET` keeps sign-ins across restarts. `web/` is the React UI: `npm run build` there writes `web/dist`, which the server serves, and `npm run typecheck` checks it. From the root: `node fixtures/generate.ts` regenerates the scenarios and answer keys; `node eval/verify-checks.ts` cross-checks the trusted checks against the generator; `node eval/leak-scan.ts` is the isolation check; `node eval/score.ts [run id ...]` scores saved runs against the answer keys (free); `node --env-file=server/.env eval/run.ts <scenario ...> [--runs n]` runs the isolation check then fresh Spark runs and scores them (about $0.30 a run); `node --test eval/*.test.ts` tests the scorer. In `server/`, `IGI_RENDER_OUT=<dir> node --test test/render.test.ts` also writes the stress PDFs, and `node scripts/pdf-pages.ts <out dir> <pdf ...>` turns PDFs into page images for inspection.
- Evaluation isolation (spec §15.2): `server/` never imports from `eval/` or `fixtures/generate.ts`, and prompts, tool descriptions and data descriptions never name expected findings. Development scenarios may be used for tuning; holdout scenarios are written after the freeze.
